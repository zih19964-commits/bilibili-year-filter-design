# GitHub Release 发布

本流程将一个已经验证的提交发布为 GitHub Release。下面的 <版本号> 应替换为已经统一到项目各入口的版本，例如 0.1.0；标签使用 v0.1.0 形式。

## 1. 推送发布提交

确认版本提交已经存在后，推送目标分支：

    git push origin <主分支>

然后创建并推送版本标签：

    git tag -a v<版本号> -m "Release v<版本号>"
    git push origin v<版本号>

标签必须指向已经通过 npm test、npm run check 和 git diff --check 的提交。不要把标签指向仍在修改中的工作区，也不要用强制推送覆盖已有发布标签。

## 2. 在 GitHub 创建 Release

1. 打开仓库主页，进入 “Releases”。
2. 点击 “Draft a new release”。
3. 选择刚刚推送的标签，例如 v0.1.0。
4. 将标题填写为 Bilibili Year Filter v0.1.0。
5. 粘贴本次版本的变更说明。
6. 检查自动生成的源码压缩包和仓库链接。
7. 确认版本号、安装路径和许可证无误后发布 Release。

用户安装时应使用以下入口：

- Tampermonkey：starter/tampermonkey/bilibili-year-filter.user.js；
- Chrome / Edge：下载源码后，在扩展管理页加载 starter/extension 文件夹；
- 使用说明：[使用说明.md](../使用说明.md)。

如果额外制作 ZIP 文件，压缩包中应保留 starter/extension 这一完整目录结构，不能只上传某个 JavaScript 文件。

## 3. Release 说明模板

    ## Added

    - Tampermonkey 用户脚本；
    - Chrome / Edge Manifest V3 扩展；
    - 指定年份、最低年份和最近 N 年过滤；
    - 隐藏、灰化、折叠三种处理方式；
    - 元数据缓存、请求队列和 API fail-open 处理。

    ## Verification

    - npm test：7 passed, 0 failed；
    - npm run check：syntax check passed；
    - manifest referenced files check passed。

    ## Known limits

    - Bilibili DOM 和详情接口属于外部不稳定依赖；
    - 首页验收证据不能替代搜索、UP 主空间和其他页面类型的独立验收；
    - 年份无法可靠确认时，视频会保持显示。

## 4. 发布后检查

发布后打开 Release 页面，确认标签、源码包、变更说明和许可证链接可访问。再用干净的浏览器配置分别安装 Userscript 和扩展，至少验证设置面板、年份过滤、动态加载和恢复默认功能。
